가설 두 개를 실측했다. 좌표 수동 지정은 효과가 없었고(폐기), 지역별로 이기는 모델이 다르다는 것은 확증됐다. 그 결과 "Windfinder = WW3이므로 ncep으로 통일"이라는 1차 결론을 정정한다. 아래 2차 검증 절 참조.

배경 / 현재 파이프라인

지금은 이렇게 수집한다

Cloud Run에서 3시간마다 server.py의 수집 루프가 돈다. 해변 32곳을 순회하면서 소스 두 개를 호출하고, 시각별로 병합해 Firestore에 저장한다.

  • 기상청 단기예보 (forecast_api.py) — 위경도를 5km 격자 nx, ny로 변환해 조회. 풍향·풍속·기온·강수와 함께 파고(WAV)를 받는다.
  • Open-Meteo Marine (open_meteo.py) — 파고·파향·수온 3개 항목만 요청한다.

저장 경로는 regions/{region}/{beach_id}/{YYYYMMDDHHMM}이고, 0·3·6·9·12·15·18·21시만 남긴다(storage.py:10). 같은 시각에 두 소스 값이 wave_height(기상청)와 om_wave_height(Open-Meteo)로 나란히 저장되는데, 둘 중 무엇을 믿어야 하는지에 대한 규칙은 코드에 없다.

발견 1 / 샘플링 지점

어느 바다를 보고 있는지가 문제였다

코드만 읽어서는 보이지 않았다. 실제로 API를 호출해 요청한 좌표와 응답에 돌아온 격자 좌표를 비교하자 드러났다. Open-Meteo는 응답에 자기가 사용한 격자의 위경도를 실어 보내는데, 현재 코드는 이 값을 읽지 않고 버린다.

open_meteo.py:35의 cell_selection: "sea"는 "요청한 칸이 육지면 가장 가까운 바다 칸으로 옮겨서 달라"는 뜻이다. 해변은 바다와 육지의 경계에 있으니 거의 항상 옮겨진다. 문제는 그 이동 거리다.

해변별로 다른 건 결국 같은 스웰이 그 해변에 어떻게 들어오느냐다. 해변이 바라보는 방위, 스웰이 열린 각도 범위, 곶이나 섬에 가려지는지. 그러려면 locations.json에 shore_normal_deg와 swell_window_deg가 필요한데 지금은 이 정보가 아예 없어서 계산 자체가 불가능하다.

발견 2 / 기준의 재설정

정답은 부이가 아니라 Windfinder다

처음엔 기상청 해양부이 실측을 기준으로 삼으려 했다. 그런데 사용자는 부이 데이터를 보지 않는다. 사용자가 비교하는 대상이 기준이어야 한다. 우리 앱이 0.3m라 하고 Windfinder가 1.1m라 하면, 물리적으로 누가 맞든 사용자는 우리가 틀렸다고 한다.

그래서 Windfinder가 무엇을 쓰는지 확인했다.

Our global wave forecasts are computed with the global wave forecast model WW3 run by the American Weather Service NOAA. windfinder.com/help/usage/waves.htm

지역 고해상도 모델(EWAM)은 지중해·발트해·오대호에만 적용된다. 한국은 전지구 WW3 그대로다. 그리고 WW3 = NOAA GFS-Wave = Open-Meteo의 ncep_gfswave025 / ncep_gfswave016이다.

핵심

Windfinder와 같은 모델을 우리가 이미 호출할 수 있다. 현재 쓰는 best_match는 한국에서 meteofrance_wave(MFWAM)로 해석된다 — Windfinder와 다른 계열이다.

2026-08-28 정정

"Windfinder = WW3이므로 ncep으로 바꾸면 자동으로 맞는다"는 결론은 과했다. 동해에서는 성립하지만 제주에서는 ncep이 오히려 하위권이다. Windfinder 자체 설명에도 "a blend of regional and global models"라고 되어 있어 WW3 단일이 아니다.

같은 날, 반대의 결론

Windfinder는 13~16초 롱 스웰을 보여준다 — 깨끗한 서핑 각이다. 우리가 쓰는 모델은 4~5초, 잡파다. Windfinder는 "나가야 하는 날", 우리 앱은 "안 나가는 날"이라고 말하고 있다. 숫자가 좀 다른 수준이 아니라 결론이 반대다.

+0.5보정값의 정체가 드러났다

storage.py:123은 모든 해변, 모든 시각의 파고에 +0.5를 더한다. 이 값을 적용한 실제 저장값을 Windfinder와 비교하면 왜 이게 들어갔는지 짐작이 간다.

진단

모델은 지역별로 다르다

1차 조사에서 세운 가설 두 개를 실제로 측정했다. 비교 기준은 같은 날 같은 좌표의 Windfinder 값이다. 과거 재분석 값이 섞이지 않도록 당일 예보끼리 대조했다.

검증된 지역은 동해(속초)와 제주뿐이다. 부산·서해/남해는 대조 데이터가 없다.

파고로 고른 모델이 파주기까지 맞지는 않는다. 제주 8/28 기준 Windfinder는 10~11초인데 1위인 ecmwf_wam025는 5.4~7.3초다. 파주기는 저장하되 앱 노출은 Phase 2로 미룬다.

참고 조사 / 기상청 부이 API

실측 검증은 절반만 가능하다

기준을 Windfinder로 옮겼지만, 신뢰도 표시용으로 실측이 여전히 쓸모 있어서 조사했다. 엔드포인트 3종 모두 실존을 확인했고(키 없이 호출 시 401), 지금 forecast_api.py가 쓰는 것과 같은 API 허브·같은 authKey라 인증 코드를 새로 짤 필요가 없다.

지점 공백

동해 부이는 동해·포항·울릉도-독도·울산·울진·동해78·동해57 7개다. 속초·강릉·양양·고성이 없다. 우리 해변 32곳 중 16곳(절반)이 이 구간에 몰려 있는데 가장 가까운 게 동해 부이(약 55km+)다. 연안용 파고부이도 동해안은 죽변(울진) 하나, 제주는 구엄·신창(둘 다 서·서북부)뿐이라 우리 제주 해변(북동·남부)과 방향이 안 맞는다.

정확한 거리는 getWaveBuoyLstTbl(파고부이 지점일람표)로 좌표를 받아야 확정된다. 이 세션 환경에는 KMA_API_KEY가 없어 미확인 상태다.

계획이 이렇게 바뀐다

Phase 1 / Phase 2 분리 원칙

Phase 1은 스키마를 깨지 않는 버그 수정과 모델 교체만 한다. 기존 평면 필드(om_wave_height 등)는 이름을 유지한 채 값만 정상화되므로 iOS 클라이언트는 수정이 필요 없다. 새로 추가하는 필드는 처음부터 Phase 2 최종 이름(wave.period_s 등)으로 넣어, 클라이언트가 Phase 2 때 한 번만 바뀌도록 한다.

마이그레이션 비용은 사실상 없다

예보 문서는 3시간마다 덮어써지고 항상 미래 3일치만 유지되며, cleanup_old_forecasts.py가 10일 지난 문서를 지운다. 배포 후 며칠이면 전부 새 값으로 교체된다. 다만 merge=True라서 Phase 2에서 필드 이름을 옮길 때는 옛 필드를 명시적으로 지워야 한다.

짚어둘 건, 이건 "더 정확해진다"가 아니라 "Windfinder와 어긋나지 않는다"라는 것이다. 어느 모델이 물리적으로 제일 맞다는 보장은 없다. 다만 사용자 불만을 기준으로 삼는다면 이게 맞는 선택이다.

미결 / 다음 단계

답이 필요한 것들

Q1

제주 격자는 따로 풀어야 한다 — 해결됨 8/28

격자 좌표가 아니라 모델 선택 문제였다. 제주에 ecmwf_wam025를 쓰면 MAE 0.150 → 0.075로 개선된다. 좌표를 옮기는 방식은 효과가 없어 폐기했다.

Q1′

미검증 지역의 모델을 어떻게 정하나

부산·서해/남해는 Windfinder 대조 데이터가 없다. Phase 1에서는 기본값으로 두고, 대조 스크립트로 데이터를 쌓은 뒤 결정한다.

Q2

해변별 노출도를 어디까지 계산할 것인가

해변별로 다른 값을 계산해서 보여주는 건 결국 추정이다. 지금처럼 양양 6곳이 같은 값인 게 정직하지만 앱 가치는 떨어진다. 계산하되 신뢰도를 함께 표시하는 쪽이 맞는지 결정이 필요하다.

Q3

shore_normal_deg를 누가 채우나

32개 해변의 방위각은 좌표만으로 정확히 뽑을 수 없다 — 해안선 형상을 봐야 한다. 해안선 기하로 초안은 만들 수 있지만, 실제 스팟을 아는 사람의 검수가 필요하다.

Q4

저장 단위를 일별 1문서로 바꿀 것인가

3시간 간격 제약은 비용 때문으로 보인다. {beach_id}/{YYYYMMDD} 안에 24시간 배열로 넣으면 읽기가 24회 → 1회로 줄면서 1시간 해상도를 얻는다. 정확도와 비용이 동시에 개선되는 유일한 항목이다.

조사 방법 — Open-Meteo Marine API를 해변 32곳 × 모델 6종으로 직접 호출해 응답 격자 좌표와 하버사인 거리를 계산했고, Windfinder 공개 예보 페이지의 수치를 같은 좌표·같은 날짜로 대조했다. 코드 결함은 해당 라인을 직접 실행해 재현 확인했다. 2차 검증(8/28)은 과거 재분석 값이 섞이는 것을 피하기 위해 당일 예보끼리 대조했고, 좌표 스윕은 앞바다 방향 0/5/10/15/20km 오프셋으로 확인했다.
