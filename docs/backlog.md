### 1. 좌표 이상 자동 감지 — 진행 가능

**왜.** 영덕 부흥·고성 천진 좌표가 **1년 반 동안 틀려 있었는데 아무도 몰랐다.**
`cell_selection=sea` 가 육지 좌표든 엉뚱한 좌표든 가장 가까운 해상 격자를 찾아
그럴듯한 숫자를 돌려주기 때문이다. `null` 도 에러도 안 난다. 재발하면 또 모른다.

**어떻게.** 수집이 이미 `marine_source.snap_distance_km` 를 계산해 저장한다.
임계값을 넘는 해변을 모아 기존 알림 경로로 보낸다 —
`app/services/collection.py:211` 의 `alert_messages` 리스트에 항목을 추가하면
`send_telegram_alert` 가 한 번에 보낸다. 새 전송 경로를 만들 필요가 없다.

**임계값 근거** (2026-09-27 운영 Firestore 32곳 실측):
스냅거리 중앙값 8.7km · 최대 18.6km(함덕). 정상 범위가 ~19km 이므로
**25km 를 경고선**으로 잡는다. 고치기 전 영덕 부흥이 14.8km 였으니 이 기준으로는
안 걸렸겠지만, 좌표가 크게 어긋나면(천진은 21.6km 떨어진 지점을 보고 있었다)
걸린다. 너무 낮게 잡으면 매 수집마다 울려서 무시하게 된다.

**완료 조건**
- [ ] 수집 로그에 임계 초과 해변이 뜬다
- [ ] 텔레그램 알림 문구에 해변 이름·거리가 들어간다
- [ ] 임계값이 `config.json` 에 있다 (코드에 박지 않는다 — 근거가 실측 1회뿐이다)
- [ ] 자격증명 없이 로직만 돌려 확인 (AGENTS.md 「자격증명 없이 로직만 돌려보기」)

**주의.** `run_collection()` 을 운영 Firestore 에 붙은 채 돌리면 **7일 지난 문서를

### 2. 롤업에 지점별 편향 표 — 진행 가능

**왜.** 10/1 에 보정계수를 판단하려면 지점별 편향·σ·표본수를 한눈에 봐야 하는데,
지금 `compare_rollup` 은 지점마다 따로 출력해서 비교가 안 된다. 2026-09-27 에
임시 스크립트로 만들어 봤고 그 형태가 쓸 만했다.

**어떻게.** `scripts/compare_rollup.py` 에 전체 요약 표를 추가한다. 지점별로
**그 지역이 실제 쓰는 모델**(`config.json` 의 `region_models`)의 편향만 모은다 —
모델이 섞이면 의미가 없다. 판정 규칙은 기존과 같다.

| 판정 | 조건 |
|---|---|
| 표본부족 | n < 5 |
| 불필요 | \|편향\| ≤ 0.05m |
| **가능** | σ < \|편향\|/2 |
| σ초과 | 그 외 — 상수화 금지 |

`grid_coverage.json` 을 읽어 **적용 가능 해변**을 같은 줄에 찍는다. 적용할 해변이
0곳인 지점(`ulsan`·`yeosu`)의 편향은 구해도 쓸 데가 없다는 게 바로 보여야 한다.

**완료 조건**
- [ ] 지점별 한 줄: 모델 · 표본수 · 편향평균 · 편향σ · 판정 · 적용 해변
- [ ] 적용 해변 0곳이면 그렇다고 표시
- [ ] 기존 지점별 상세 출력은 유지 (요약을 위에 덧붙인다)

### 4. 천진 방위 갱신 — XS

`data/shore_normal.json` 의 고성 천진 값(방위 50°·스웰창 30°)이 **옛 좌표
(13km 북쪽) 기준**이다. 스웰창이 30°로 좁게 나온 것도 옛 좌표가 만 안쪽을
찍고 있었기 때문일 가능성이 크다.

```sh
.venv/bin/python3 -m scripts.shore_normal --region sokcho --save
```

### 5. 남애3리 좌표 — S

**현재 `37.9694` 가 죽도 `37.9723` 과 0.4km 다.** 남애리는 현남면 남쪽
(남애서핑클럽 매바위길 192-1 / 남애리 548-2)이라 거의 확실히 틀렸다.
고도도 26m 다.

```sh
.venv/bin/python3 -m scripts.shore_normal --region yangyang
```

바다 방위·고도를 본 뒤 해안선을 스캔해 후보를 잡는다. 지도 스크린샷은 이미 받았다.

### 6. 동해 대진 좌표 — S

고도 27m. 동해시 대진동(라라서프 일출로 462-1 / 대진동 45-3). 현재 좌표
`37.5383, 129.1042` 의 위치 자체는 대략 맞아 보이므로 #5 보다 우선순위가 낮다.

### 7. 중문 — 건드리지 말 것

고도 62m 로 가장 높지만 **주상절리 절벽 지형이라 DEM 이 절벽 위를 찍었을
가능성이 크다.** 무엇보다 `jungmun` 대조 지점과 **격자가 일치**하므로
(`grid_coverage.json`) 좌표를 옮기면 오히려 어긋난다. 실제 입수 지점을 아는
사람이 명백히 틀렸다고 할 때만 손댄다.

## 결정이 필요한 것

### 10. 노출도 변환 — 해변별 차등

**이게 "해변마다 다른 값" 요구의 본체다.** 양양 6곳이 같은 값인 건 격자 붕괴
때문이고 모델로도 Windfinder 로도 안 풀린다.

재료는 준비됐다 — `shore_normal.json` 32곳 + 수집 중인 파향.
**막는 것은 공식 선택과 #9(방위 검수)다.**

| | 절대 감쇠 | 상대 노출도 |
|---|---|---|
| 식 | `H × cos(θ)^k` | `H × cos(θ)^k / mean(지역)` |
| Windfinder 일치 | **잃는다** | 유지 |
| 물리적 정직성 | 높다 | 정규화로 일부 포기 |

2026-09-27 시뮬레이션에서 드러난 것: 절대 감쇠는 **모든 해변을 줄인다**
(21시 0.40m → 0.14~0.23m). 지금 파고는 Windfinder 와 4~6cm 로 맞는데
감쇠를 걸면 멀어진다. 목표가 「Windfinder 와 비슷하게」라면 상대 노출도가 맞다.

정할 것: 공식 · `k` 값 · 창 밖 처리(완전 차단 vs 감쇠) · 신뢰도 노출 여부.

### 11. 방위 검수 32곳

`docs/marine-data-audit.md` Q3 이 "실제 스팟을 아는 사람의 검수가 필요하다"고
적어둔 그 작업이다. **틀린 방위로 파고를 조정하면 지금보다 나빠지므로 #10 의
선행 조건이다.**

현재 검수 대상 (`scripts/shore_normal.py` 출력):
- 다대포 ↔ 광안리 — 18.5km 인데 방위 차 90°
- 고성 천진 30° · 고흥 남열 30° — 스웰 창이 좁다 (천진은 #4 로 갱신하면 바뀔 것)

### 12. develop 머지

브랜치가 `develop` 보다 20커밋 이상 앞서 있다. 검증 도구 변경이 대부분이지만
**`locations.json` 좌표 3곳 수정은 운영 수집에 영향이 있다**(영덕 부흥·고성
천진은 격자가 바뀐다). #3 과 함께 결정하는 것이 자연스럽다.

### 13. busan 대조 지점

송정·다대포·광안리 3곳이 대조 지점 없이 기본 모델로 간다. Windfinder 에
`songjeong`·`dadaepo`·`gwangalli`·`haeundae`·`gijang`·`ilgwang`·`busan` 이
전부 404 다. 오너가 windfinder.com 에서 부산 지점을 찾아주기로 했다.

찾으면 확인할 것: 파고·파주기가 8/8 로 파싱되는지, 이름에 `(Tide)` 나
`virtual buoy` 가 붙지 않았는지(조위 관측소·모델 산출점은 기준값으로 부적합).

## 다른 저장소

### 14. iOS 파고 우선순위 뒤집기 — P0

**화면 파고의 병목이다.** iOS 가 기상청 `wave_height` 를 우선 읽는데 그 값이
8시각 전부 `0.5` 고정이다. 백엔드 개선이 화면에 도달하지 않는다.

| 차이 | 크기 |
|---|---|
| 모델 1·2위 편향제거 MAE | 0.001m |
| 모델 편향 | 0.009~0.201m |
| **기상청 상수 vs Open-Meteo** | **0.14~0.42m** |

**이 수정 하나가 4주 모델 튜닝보다 10배 이상 크다.** 진단과 해법은
`docs/ios-migration.md` 「P0 · 파고 우선순위를 뒤집어야 한다」에 이미 있다.
수정 위치는 `piriram/DoSurf-iOS` 이므로 이 저장소에서는 할 수 없다.
