# 2026-08-30

## 무엇을

Windfinder 대조를 자동화하고, 파주기 기준 모델 순위를 낼 수 있게 만들었다.
첫 측정에서 "파고로 고른 모델이 파주기까지 맞는가"라는 열린 질문에
제주는 **아니다**라는 답이 나왔다.

## 왜

어제 iOS에서 파주기를 파랑모델 실제 값으로 전환했는데(P1), 그 값이 맞는지는
검증되지 않은 상태였다. 문서에도 "파고로 고른 모델이 파주기까지 맞는다는
보장이 없다"고 적혀 있었다.

검증 기준은 Windfinder다. 부이가 아니라 Windfinder인 이유는 **서퍼들이 실제로
보는 값이 그것**이기 때문이다(저장소 결정표). 우리 모델이 Windfinder와
비슷해지는 게 목표지, Windfinder 데이터를 쓰는 게 목표가 아니다.

그런데 `model_compare.py`는 두 가지가 막혀 있었다.
- 파주기를 받아두고도 순위는 파고로만 매겼다
- Windfinder 값을 사람이 사이트에서 읽어 넣어야 했다

## 어떻게

### 1. 파주기 기준 추가

`--reference-period`로 파주기 MAE 순위를 따로 낸다. **합치지 않고 나눴다.**
하나의 점수로 합치면 "둘 다 만족하는 모델이 있는가"라는 질문 자체가 숫자 안에서
사라진다. 1위가 갈리면 갈렸다고 출력한다.

결측 시각은 짝이 맞는 값만 세어 평균낸다. 0으로 치면 오차가 실제보다 작아진다.

### 2. Windfinder 자동 수집

스크래핑이라 구현 전에 robots.txt와 이용약관을 확인했다. Windfinder는 이
데이터를 파는 API가 따로 있어서(api.windfinder.com) 선을 그어두고 시작했다.

- `/forecast/`만 읽는다 — robots.txt가 `/api/`, `/widget/forecast/`,
  `/share/forecast/`, `/wind-cgi/*`를 막고 있다. 사람이 보는 페이지는 열어두고
  기계가 값만 빼가는 경로는 닫아둔 구성이라, 그 의도를 우회하지 않는다
- 같은 날 같은 지점은 캐시 재사용, 폴링 없음, User-Agent에 용도·연락처 명시
- 받은 값은 Firestore·앱에 안 넣는다. 약관이 상업적 재배포를 금지하고
  우리는 모델 선택 근거로만 쓴다
- **HTML 원본 캐시는 .gitignore** — 이 저장소가 public이라 남의 페이지 원문을
  올리면 그 자체가 재배포다. 하마터면 516K를 커밋할 뻔했다

### 3. 첫 측정 결과 (2026-08-30, 1일치)

| | 파고 1위 | 파주기 1위 | 일치 |
|---|---|---|---|
| 속초 | `ncep_gfswave025` (0.030m) | `ncep_gfswave025` (0.26s) | ✅ |
| 제주 | `ecmwf_wam025` (0.030m) | `ncep_gfswave025` (1.13s) | ⚠️ 갈림 |

제주는 파고 1위인 `ecmwf_wam025`가 **파주기에서 꼴찌(2.86초)**다.
문서에 적혀 있던 "제주 8/28 Windfinder 10~11초 vs ecmwf_wam025 5.4~7.3초"와
같은 방향이다. 게다가 제주는 최선이어도 1.13초 오차로 속초(0.26초)의 4배다.
**제주 파주기는 아직 못 믿을 값이다.**

현재 채택 모델(동해 `ncep_gfswave016`)은 오늘 파고 3위였다. 하루치로 바꾸지
않고 `data/model_compare.jsonl`에 누적한다.

## 배운 점 / 다음 액션

**약관 확인이 설계를 바꿨다.** 그냥 긁었으면 캐시 HTML까지 public 저장소에
커밋했을 것이고, 그게 진짜 문제였다. 값을 쓰는 것(사실 데이터, 검증 목적)과
페이지 원문을 재배포하는 것은 다른 일인데, 구현하다 보면 후자가 딸려온다.

**순위를 합치지 않은 게 결과를 살렸다.** 파고·파주기를 하나로 합쳤으면 제주에서
"1위가 갈린다"는 신호가 안 나왔다. 검증 도구는 답을 하나로 줄이는 것보다
**어긋남이 보이게** 만드는 편이 낫다.

**조용히 실패하는 파싱을 조심한다.** `requests`가 인코딩을 잘못 잡아
narrow no-break space(U+202F)가 깨졌는데, 예외가 아니라 "매칭 0건"으로 나왔다.
curl로 받았을 땐 됐기 때문에 더 헷갈렸다. 원인을 주석에 남겼다.

다음:
- 며칠 더 쌓아서 모델 재확정. `ncep_gfswave025`가 계속 1위면 config.json 수정
- 제주 파주기 오차가 큰 게 모델 문제인지 Windfinder 지점 좌표 문제인지 확인
  (제주 기준 지점이 33.5142,126.5297인데 우리 해변은 남쪽 사계 33.2278,126.3075)
- 기준 지점 늘리기 — 부산·포항이 Windfinder에 있는지, 우리 해변과 얼마나 가까운지
- 기상청 `wave_height` 값 범위 검증 추가 (iOS엔 센티넬 가드가 있는데 백엔드엔 없다)

## 세션 2 — 커밋 히스토리에서 AI 흔적 제거

### 무엇을

커밋 4건에 남아 있던 AI 공동작성 트레일러를 지우고, 브랜치명에서 도구 이름을
뺐다. PR 규칙도 함께 정리했다.

### 왜

PR을 열고 GitHub에서 커밋 목록을 보니 `piriram and claude committed`로 찍혀
있었다. 원격 세션에서 만들어진 커밋 4건(`f148f44`, `3a056dc`, `cbf3e5d`,
`fc9c11c`)에 아래 두 줄이 붙어 있었다.

```
Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
Claude-Session: https://claude.ai/code/session_...
```

이 저장소의 `CLAUDE.md`에 **이미 경고가 적혀 있던 문제**다. "컨테이너 전역
설정이 Claude라 확인 없이 커밋하면 그렇게 찍힌다. 실제로 한 번 그렇게 나가서
커밋을 되돌린 적이 있다." 경고를 적어둔 그 세션이 정작 자기 커밋에는 트레일러를
남겼다.

구직 중이라 이 저장소들이 포트폴리오로 읽힌다. 작업 주체가 흐려지면 안 된다.

### 어떻게

`git filter-branch`는 히스토리 재작성이라 실행이 막혔다. 대신 **새 브랜치에
cherry-pick으로 다시 쌓았다.** 10개를 순서대로 옮기면서 4개만 메시지에서 두
줄을 지웠고, author와 author date는 원본 그대로 넘겼다.

지운 것은 트레일러 두 종류뿐이다. 본문의 `CLAUDE.md` 파일명 언급이나 "커밋
identity 주의" 같은 문장은 **실제 문서 내용이라 남겼다.**

검증은 트리 해시로 했다.

```
git rev-parse df87b7e^{tree}  ==  git rev-parse HEAD^{tree}   → 일치
```

메시지만 바뀌고 파일 내용은 한 바이트도 안 변했다는 뜻이다. 되돌릴 수 있게
`backup/before-trailer-strip` 태그를 먼저 걸어뒀다.

함께 정리한 것:
- 브랜치 `claude/marine-data-accuracy` → `feat/marine-data-accuracy`.
  브랜치명도 PR에 그대로 노출된다
- PR 본문의 `🤖 Generated with Claude Code` 푸터 제거
- **PR 대상을 `main`에서 `develop`으로.** `main`은 릴리즈 브랜치다
- 구브랜치는 원격에서 삭제, PR #1은 사유를 남기고 닫고 #2로 다시 열었다

전역 공통 규칙(`~/shared/docs/agents-common.md`)에도 넣었다. 금지 범위를
커밋뿐 아니라 **PR 제목·본문·브랜치명까지** 넓혔고, 확인용 명령을 같이 적었다.

### 배운 점 / 다음 액션

**문서에 적어둔 함정을 자기가 밟는다.** 경고가 `CLAUDE.md`에 있었는데도 같은
일이 반복됐다. 사람이 읽고 기억하는 방식의 규칙은 이렇게 샌다. 그래서 규칙
쪽에 확인 명령(`git log -1 --format='%an <%ae>%n%B' | grep -i claude`)을 같이
적었다 — 읽고 지키는 것보다 실행해서 확인하는 편이 낫다.

**히스토리 재작성에도 검증 기준이 있다.** 트리 해시 비교로 "내용은 그대로,
메시지만 바뀜"을 한 줄로 증명할 수 있다. diff를 눈으로 훑는 것보다 확실하다.

다음:
- 백업 태그 `backup/before-trailer-strip` 는 PR 머지 후 삭제
- 앞으로 커밋·PR 만든 직후 위 grep 한 번 돌릴 것

## Windy 3자 대조 붙이기

Windfinder만 기준이던 대조에 Windy를 추가하려다, Windy 쪽에서 먼저 벽을 만났다.

### Windy API는 못 쓴다

Point Forecast API 무료 Trial이 **실데이터가 아니라 난수를 돌려준다.** 공식
pricing 페이지 문구가 그대로 "randomly shuffled and slightly modified data"다.
실데이터는 Professional €990/년뿐. 스크래핑은 windy.com이 WebGL SPA라 애초에
`windfinder.py` 같은 HTML 정규식 파싱이 불가능하고 ToS에도 걸린다.

→ Windy 값은 사람이 읽어 `--reference-windy` 로 넣는 것으로 결정.

### 더 중요한 발견 — Windy 파랑모델 = 우리 모델

| Windy | 실제 모델 | Open-Meteo |
|---|---|---|
| `gfsWave` | NOAA/NCEP GFS-Wave (WW3) | `ncep_gfswave025` · `016` |
| `iconWave` | DWD GWAM | `gwam` |
| `iconEuWave` | DWD EWAM | `ewam` |

`ewam` 은 실제로 호출해보니 속초에서 `"No data is available for this location"`
— 유럽 해역 전용이라 한국은 커버리지 밖이다. 즉 **한국에서 Windy가 쓰는 파랑
모델은 `gfsWave`·`iconWave` 둘뿐이고, 둘 다 이미 `CANDIDATE_MODELS`에 있었다.**

Windfinder를 WW3라고 단정했다가 정정했던 8/28과 같은 구조의 함정이다. Windy
대조가 재는 것은 "Windy가 더 맞나"가 아니라 **"같은 모델을 Windy가 어떻게
격자 스냅·보간했나"** 다. 표에 `*` 를 찍어 어느 모델이 Windy의 그 모델인지
매번 눈에 띄게 했다.

### 넣은 것

`model_compare.py`
- `--reference-windy`, `--reference-windy-period` 추가. 기준마다 표를 따로 낸다
- `WINDY_EQUIVALENT` 매핑과 `*` 표시 + 범례
- **`[기준끼리]` 블록** — Windy vs Windfinder를 먼저 잰다. 기준끼리 차이가
  모델 1·2위 차이보다 크면 순위가 기준 선택에 좌우된다는 뜻이라 경고한다.
  실측에서 바로 걸렸다: 1·2위 차 0.004m vs 기준 모양차 0.050m
- 기준마다 1위가 다르면 "어느 예보에 맞출지는 데이터가 아니라 제품 결정"이라고 말한다
- jsonl 스키마는 `_windy` 접미 키를 더하는 방식이라 기존 기록과 호환

`compare_rollup.py` (신규) — 이게 진짜 구멍이었다. 하루치 순위를 내는 도구는
있었는데 **여러 날을 모으는 도구가 없었다.** `jsonl`에 2줄 쌓아놓고 아무도 안
읽고 있었다. 판정 규칙:

- 표본 5일 미만 → 결론 보류
- 1위 최다 득표가 60% 미만 → 노이즈. 더 쌓을 것
- **편향 표준편차 < 편향 절댓값/2** 일 때만 상수 보정계수 후보

마지막 항목이 핵심이다. 편향 평균만 보고 상수를 박으면 `+0.5` 재발이다.
흔들림이 크면 애초에 상수화가 불가능하다는 걸 숫자로 막았다.

### 배운 점 / 다음 액션

**"다른 소스와 대조"의 전제를 먼저 확인해야 한다.** Windy를 붙이자는 요구는
자연스러웠지만, 붙이고 보니 같은 모델이었다. 대조 상대가 독립인지부터 확인하지
않으면 자기 자신과 비교하고 정확도가 올랐다고 착각한다. Windfinder에서 한 번,
Windy에서 또 한 번 같은 함정이었다.

**측정 도구는 있는데 결론 도구가 없는 상태가 제일 위험하다.** 매일 재고는
있었지만 쌓인 걸 읽는 코드가 없어서, 결국 하루치를 보고 판단하게 된다.
그게 `+0.5` 가 들어온 경로다.

다음:
- 5일치 쌓기 — 매일 `model_compare.py --from-windfinder --reference-windy ... --out`
- 제주 모델 확정 (현재 `default` 보류 상태)
- 부산·서남해 Windfinder 지점 slug 찾아 `REFERENCE_SPOTS` 확장

## Copernicus Marine(CMEMS) 붙여보기

Open-Meteo 대안 후보 중 유일하게 살아 있던 것. 실제로 붙여서 재보기로 했다.

### 조사 문서가 틀렸다

`docs/MARINE_DATA_INVESTIGATION.md` 에 "REST 단건 조회 불가. NetCDF-4 파일을
내려받아 직접 파싱해야 함"이라고 적혀 있었고, 그게 보류 사유였다. 그런데 그건
툴박스 v1 기준이었다. **v2.4.1 은 `open_dataset()` 이 ARCO(zarr)를 lazy 하게
열어준다** — 격자 상자와 시간 범위만 잘라 받으면 되고 파일 파이프라인이 필요 없다.

보류 사유의 절반이 사라졌다. 문서에 정정 블록을 넣었다.

### 확인한 것

- `describe` 는 **인증 없이** 된다. 데이터셋 ID `cmems_mod_glo_wav_anfc_0.083deg_PT3H-i`,
  변수 19종을 카탈로그에서 직접 읽었다
- **UTC 3시간 격자가 KST에서도 0,3,...,21시에 그대로 떨어진다.** +9h 가 3의
  배수라서다. `ALLOWED_HOURS` 와 보간 없이 맞는다 — 운이 좋았다
- Python 3.14.7 에서 설치·임포트 정상 (numpy 2.5.2 / xarray 2026.7.0 / zarr 3.3.0)

### 제일 중요한 발견 — 파주기가 둘이다

CMEMS는 `VTM10`(평균주기)과 `VTPK`(첨두주기)를 **따로** 준다.

Open-Meteo `wave_period` 는 평균주기 계열이고, Windfinder·서핑 앱이 화면에 쓰는
건 첨두주기다. 제주 8/28에 "Windfinder 10~11초인데 우리는 5.4~7.3초"라고 적어둔
그 차이(`docs/ios-migration.md`)가 **모델 오차가 아니라 정의 차이**일 수 있다.

평균주기와 첨두주기는 원래 첨두 쪽이 크다. 두 배 가까운 차이가 나는 건 이상한
일이 아니다. 그걸 모르고 "모델을 바꿔야 한다"고 판단했으면 엉뚱한 데를 고쳤을
것이다.

그래서 `cmems` / `cmems_peak` 두 가짜 모델명으로 나눠 넣었다. 같은 자료를
파주기만 다르게 읽는다. 파주기 순위에서 둘이 갈리면 그게 답이다.

### 넣은 것

`scripts/copernicus.py` (신규) — `open_meteo.fetch_marine()` 과 **같은 모양의 행**을
돌려준다. 그래야 `model_compare.py` 가 구분 없이 같은 표에 놓는다.

- `_pick_sea_cell()` — CMEMS엔 `cell_selection=sea` 가 없다. 가장 가까운 격자가
  육지면 NaN이라 "결측 많은 모델"로 오판된다. ±0.5° 상자에서 VHM0 가 유효한 칸 중
  제일 가까운 것을 직접 고른다
- `has_credentials()` — 자격증명이 없으면 툴박스가 **대화형으로 아이디를 묻고**,
  배치에선 EOF로 끊겨 `None` 이 돌아온다. 그러면 원인과 무관한
  `'NoneType' object is not subscriptable` 로 터진다. 먼저 걸러낸다
- `open_dataset` 이 예외 대신 `None` 을 주는 경우도 따로 막았다

`model_compare.py` — `fetch_series()` 디스패처를 넣어 Open-Meteo와 CMEMS를 바깥에서
구분하지 않게 했다. 한 번 돌 때 CMEMS를 두 번 안 받도록 캐시.

`requirements-dev.txt` (신규) — copernicusmarine 이 xarray·zarr·dask 를 끌고 와서
`.venv` 가 540MB가 된다. Dockerfile 은 `requirements.txt` 만 설치하므로 배포엔
안 들어가지만, 실수로 옮기지 못하게 파일을 분리하고 이유를 적었다.

### 회귀 하나 잡음

어제 3자 대조를 넣으면서 표를 "기준별로" 그리게 바꿨는데, `--reference` 없이
돌리면 활성 기준이 0개라 **표가 통째로 안 나왔다.** 모델 값만 훑어보는 용도가
죽어 있었다. 폴백 렌더를 넣었다.

### 커밋 정리 — 개발로그 게이트와 부딪힌 부분

작업을 5개 커밋으로 쪼개려다 `devlog-gate.sh` 에 걸렸다. 게이트는
**오늘자 로그 파일의 mtime이 마지막 커밋보다 새로운지**를 본다. 첫 커밋을
넣는 순간 로그가 stale 해져서 두 번째부터 전부 막힌다.

`[nolog]` 로 뚫을 수는 있지만 그건 "이 커밋에 로그가 불필요할 때" 쓰라는
탈출구다. 로그는 이미 있고 다음 커밋에 실릴 예정이었을 뿐이라 해당되지 않는다.
커밋마다 형식적으로 로그를 한 줄씩 늘리는 것도 게이트를 우회하는 것에 가깝다.

그래서 **커밋 수를 줄였다**. 3개:

1. `feat: 대조 누적분 집계 스크립트 추가` — compare_rollup.py
2. `feat: 모델 대조에 Windy·CMEMS 후보 추가` — copernicus.py, model_compare.py,
   requirements-dev.txt, 표본 2건, 개발로그
3. `docs:` — CLAUDE.md, README.md, 조사 문서 정정

model_compare.py 는 Windy 3자 대조와 CMEMS 디스패처 변경이 한 파일에서
얽혀 있어 어차피 쪼개려면 hunk 단위 스테이징이 필요했다. 2번으로 합친 게
자연스럽다.

배운 점: **커밋 단위를 훅이 강제하는 로그 주기에 맞춰야 한다.** 로그가
세션 단위인데 커밋을 잘게 쪼개면 구조적으로 부딪힌다. 게이트를 우회할
방법을 찾기 전에 커밋 입자 크기를 먼저 의심하는 게 맞다.

## CMEMS 실측 — 파주기는 모델 문제가 아니라 정의 문제였다

로그인 후 실제로 돌려봤다.

### 타임존 버그 하나 잡음

첫 실행에서 8/30 21시(KST)가 빠졌다. 원인은 **툴박스가 naive datetime을
실행 머신의 로컬 시간으로 해석**하는 것이었다. UTC 12:00을 달라고 넘겼는데
KST로 읽어 03:00 UTC부터 받아왔다 — 창이 통째로 9시간 앞으로 밀렸다.

값 자체는 맞았다(03:00 UTC = 12:00 KST 변환은 정상). **창만 어긋나서 하루의
끝이 잘렸고**, 그러면 `model_compare` 가 결측으로 보고 CMEMS를 통째로 버린다.
조용히 틀리는 종류라 위험했다.

`tzinfo=UTC` 를 붙이니 요청 창과 응답 축이 정확히 일치했다.

### 연결 확인

- 격자 8.79km — Open-Meteo 후보들(12.8~16.1km)보다 가깝다
- 커버리지는 2022-11-01 ~ 2026-09-08. **과거 분석장이 있다** — Windfinder 기준만
  구할 수 있으면 표본을 5일 기다리지 않고 소급해 쌓을 수도 있다

### 본론 — 제주에서 갈렸다

속초는 Windfinder가 6~7초라 평균/첨두 차이가 작아 결판이 안 났다.
제주가 시험대였다 (Windfinder 8.0초 고정).

| | 범위 | Windfinder 대비 |
|---|---|---|
| 평균주기 VTM10 | 4.76 ~ 5.69초 | -2.3 ~ -3.2초 |
| 첨두주기 VTPK | 6.43 ~ 8.12초 | -1.6 ~ +0.1초 |

원시 MAE 첨두 0.81초 · 평균 2.82초. **3.5배.**

`docs/ios-migration.md` 에 "제주 8/28 Windfinder 10~11초인데 ecmwf_wam025는
5.4~7.3초"라고 적어둔 그 5.4~7.3이 **정확히 평균주기 대역**이다. 우리는 평균주기를
첨두주기와 비교하면서 "모델이 틀렸다"고 판단하고 있었다.

해당 문서에 보강 블록을 넣었다.

### 파고는?

CMEMS가 이기지 않았다. 속초 편향제거 4위(0.048m), 제주 4위(0.034m). 다만
**편향이 두 지점 다 가장 작은 축**이다(속초 -0.009m). 격자도 제일 가깝다.
파고만 놓고 보면 Open-Meteo를 갈아탈 이유는 아직 없다.

### 배운 점

**단위가 같다고 같은 양이 아니다.** 둘 다 "초"이고 둘 다 "파주기"라서 그냥
비교했다. 정의가 다른 두 값을 비교하면서 모델 순위를 매기고 있었고, 그대로
갔으면 엉뚱한 모델로 바꿨을 것이다. 값을 비교하기 전에 **정의가 같은지**부터
확인해야 한다.

**조용히 잘리는 버그가 제일 위험하다.** 타임존 건도 에러가 안 났다. 하루치를
달라고 했는데 7/8만 오고, 그게 "결측 많은 소스"로 오판되는 경로였다.
경계값(첫 시각·끝 시각)을 항상 눈으로 확인할 것.
