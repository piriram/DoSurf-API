# 2026-08-30

## 무엇을

Windfinder 대조를 자동화하고, 파주기 기준 모델 순위를 낼 수 있게 만들었다.
첫 측정에서 "파고로 고른 모델이 파주기까지 맞는가"라는 열린 질문에
제주는 **아니다**라는 답이 나왔다.

## 왜

어제 iOS에서 파주기를 파랑모델 실제 값으로 전환했는데(P1), 그 값이 맞는지는
검증되지 않은 상태였다. 문서에도 "파고로 고른 모델이 파주기까지 맞는다는
보장이 없다"고 적혀 있었다.

검증 기준은 Windfinder다. 부이가 아니라 Windfinder인 이유는 **서퍼들이 실제로
보는 값이 그것**이기 때문이다(저장소 결정표). 우리 모델이 Windfinder와
비슷해지는 게 목표지, Windfinder 데이터를 쓰는 게 목표가 아니다.

그런데 `model_compare.py`는 두 가지가 막혀 있었다.
- 파주기를 받아두고도 순위는 파고로만 매겼다
- Windfinder 값을 사람이 사이트에서 읽어 넣어야 했다

## 어떻게

### 1. 파주기 기준 추가

`--reference-period`로 파주기 MAE 순위를 따로 낸다. **합치지 않고 나눴다.**
하나의 점수로 합치면 "둘 다 만족하는 모델이 있는가"라는 질문 자체가 숫자 안에서
사라진다. 1위가 갈리면 갈렸다고 출력한다.

결측 시각은 짝이 맞는 값만 세어 평균낸다. 0으로 치면 오차가 실제보다 작아진다.

### 2. Windfinder 자동 수집

스크래핑이라 구현 전에 robots.txt와 이용약관을 확인했다. Windfinder는 이
데이터를 파는 API가 따로 있어서(api.windfinder.com) 선을 그어두고 시작했다.

- `/forecast/`만 읽는다 — robots.txt가 `/api/`, `/widget/forecast/`,
  `/share/forecast/`, `/wind-cgi/*`를 막고 있다. 사람이 보는 페이지는 열어두고
  기계가 값만 빼가는 경로는 닫아둔 구성이라, 그 의도를 우회하지 않는다
- 같은 날 같은 지점은 캐시 재사용, 폴링 없음, User-Agent에 용도·연락처 명시
- 받은 값은 Firestore·앱에 안 넣는다. 약관이 상업적 재배포를 금지하고
  우리는 모델 선택 근거로만 쓴다
- **HTML 원본 캐시는 .gitignore** — 이 저장소가 public이라 남의 페이지 원문을
  올리면 그 자체가 재배포다. 하마터면 516K를 커밋할 뻔했다

### 3. 첫 측정 결과 (2026-08-30, 1일치)

| | 파고 1위 | 파주기 1위 | 일치 |
|---|---|---|---|
| 속초 | `ncep_gfswave025` (0.030m) | `ncep_gfswave025` (0.26s) | ✅ |
| 제주 | `ecmwf_wam025` (0.030m) | `ncep_gfswave025` (1.13s) | ⚠️ 갈림 |

제주는 파고 1위인 `ecmwf_wam025`가 **파주기에서 꼴찌(2.86초)**다.
문서에 적혀 있던 "제주 8/28 Windfinder 10~11초 vs ecmwf_wam025 5.4~7.3초"와
같은 방향이다. 게다가 제주는 최선이어도 1.13초 오차로 속초(0.26초)의 4배다.
**제주 파주기는 아직 못 믿을 값이다.**

현재 채택 모델(동해 `ncep_gfswave016`)은 오늘 파고 3위였다. 하루치로 바꾸지
않고 `data/model_compare.jsonl`에 누적한다.

## 배운 점 / 다음 액션

**약관 확인이 설계를 바꿨다.** 그냥 긁었으면 캐시 HTML까지 public 저장소에
커밋했을 것이고, 그게 진짜 문제였다. 값을 쓰는 것(사실 데이터, 검증 목적)과
페이지 원문을 재배포하는 것은 다른 일인데, 구현하다 보면 후자가 딸려온다.

**순위를 합치지 않은 게 결과를 살렸다.** 파고·파주기를 하나로 합쳤으면 제주에서
"1위가 갈린다"는 신호가 안 나왔다. 검증 도구는 답을 하나로 줄이는 것보다
**어긋남이 보이게** 만드는 편이 낫다.

**조용히 실패하는 파싱을 조심한다.** `requests`가 인코딩을 잘못 잡아
narrow no-break space(U+202F)가 깨졌는데, 예외가 아니라 "매칭 0건"으로 나왔다.
curl로 받았을 땐 됐기 때문에 더 헷갈렸다. 원인을 주석에 남겼다.

다음:
- 며칠 더 쌓아서 모델 재확정. `ncep_gfswave025`가 계속 1위면 config.json 수정
- 제주 파주기 오차가 큰 게 모델 문제인지 Windfinder 지점 좌표 문제인지 확인
  (제주 기준 지점이 33.5142,126.5297인데 우리 해변은 남쪽 사계 33.2278,126.3075)
- 기준 지점 늘리기 — 부산·포항이 Windfinder에 있는지, 우리 해변과 얼마나 가까운지
- 기상청 `wave_height` 값 범위 검증 추가 (iOS엔 센티넬 가드가 있는데 백엔드엔 없다)

## 세션 2 — 커밋 히스토리에서 AI 흔적 제거

### 무엇을

커밋 4건에 남아 있던 AI 공동작성 트레일러를 지우고, 브랜치명에서 도구 이름을
뺐다. PR 규칙도 함께 정리했다.

### 왜

PR을 열고 GitHub에서 커밋 목록을 보니 `piriram and claude committed`로 찍혀
있었다. 원격 세션에서 만들어진 커밋 4건(`f148f44`, `3a056dc`, `cbf3e5d`,
`fc9c11c`)에 아래 두 줄이 붙어 있었다.

```
Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
Claude-Session: https://claude.ai/code/session_...
```

이 저장소의 `CLAUDE.md`에 **이미 경고가 적혀 있던 문제**다. "컨테이너 전역
설정이 Claude라 확인 없이 커밋하면 그렇게 찍힌다. 실제로 한 번 그렇게 나가서
커밋을 되돌린 적이 있다." 경고를 적어둔 그 세션이 정작 자기 커밋에는 트레일러를
남겼다.

구직 중이라 이 저장소들이 포트폴리오로 읽힌다. 작업 주체가 흐려지면 안 된다.

### 어떻게

`git filter-branch`는 히스토리 재작성이라 실행이 막혔다. 대신 **새 브랜치에
cherry-pick으로 다시 쌓았다.** 10개를 순서대로 옮기면서 4개만 메시지에서 두
줄을 지웠고, author와 author date는 원본 그대로 넘겼다.

지운 것은 트레일러 두 종류뿐이다. 본문의 `CLAUDE.md` 파일명 언급이나 "커밋
identity 주의" 같은 문장은 **실제 문서 내용이라 남겼다.**

검증은 트리 해시로 했다.

```
git rev-parse df87b7e^{tree}  ==  git rev-parse HEAD^{tree}   → 일치
```

메시지만 바뀌고 파일 내용은 한 바이트도 안 변했다는 뜻이다. 되돌릴 수 있게
`backup/before-trailer-strip` 태그를 먼저 걸어뒀다.

함께 정리한 것:
- 브랜치 `claude/marine-data-accuracy` → `feat/marine-data-accuracy`.
  브랜치명도 PR에 그대로 노출된다
- PR 본문의 `🤖 Generated with Claude Code` 푸터 제거
- **PR 대상을 `main`에서 `develop`으로.** `main`은 릴리즈 브랜치다
- 구브랜치는 원격에서 삭제, PR #1은 사유를 남기고 닫고 #2로 다시 열었다

전역 공통 규칙(`~/shared/docs/agents-common.md`)에도 넣었다. 금지 범위를
커밋뿐 아니라 **PR 제목·본문·브랜치명까지** 넓혔고, 확인용 명령을 같이 적었다.

### 배운 점 / 다음 액션

**문서에 적어둔 함정을 자기가 밟는다.** 경고가 `CLAUDE.md`에 있었는데도 같은
일이 반복됐다. 사람이 읽고 기억하는 방식의 규칙은 이렇게 샌다. 그래서 규칙
쪽에 확인 명령(`git log -1 --format='%an <%ae>%n%B' | grep -i claude`)을 같이
적었다 — 읽고 지키는 것보다 실행해서 확인하는 편이 낫다.

**히스토리 재작성에도 검증 기준이 있다.** 트리 해시 비교로 "내용은 그대로,
메시지만 바뀜"을 한 줄로 증명할 수 있다. diff를 눈으로 훑는 것보다 확실하다.

다음:
- 백업 태그 `backup/before-trailer-strip` 는 PR 머지 후 삭제
- 앞으로 커밋·PR 만든 직후 위 grep 한 번 돌릴 것

## 세션 3 — 편향과 모양을 나누고, 검증 기준 자체를 의심하게 됨

### 무엇을

"어떻게 해야 Windfinder와 경향성이 비슷해지나"라는 질문에서 출발해
`model_compare.py`에 편향·상관계수를 추가했다. 그 답을 내는 과정에서
**우리 검증 방식 자체에 구멍이 있다는 것**을 알게 됐다.

### 왜 — MAE가 두 문제를 섞고 있었다

지금까지 MAE 하나로 모델을 골랐다. 그런데 MAE는 성격이 다른 둘을 한 숫자에 섞는다.

- **편향(bias)** — 이 지점에서 늘 얼마나 높게/낮게 나오는가. 상수를 더해 고친다
- **모양(shape)** — 오르내리는 흐름이 기준과 같은가. 모델을 바꿔야 고친다

속초 실측(2026-08-30):

| 모델 | MAE | 편향 | 편향제거 MAE | 상관계수 |
|---|---|---|---|---|
| ecmwf_wam025 | 0.035 | +0.030 | 0.017 | 0.9974 |
| ncep_gfswave025 | 0.030 | −0.020 | 0.025 | 0.9934 |
| ncep_gfswave016 (현재) | 0.078 | −0.078 | 0.027 | 0.9888 |
| gwam | 0.235 | −0.235 | 0.105 | 0.9827 |

`gwam`이 답을 잘 보여준다. MAE 0.235로 꼴찌인데 편향이 정확히 −0.235이고,
빼면 0.105로 줄어든다. **틀린 게 아니라 일정하게 낮게 나올 뿐이다.**

그래서 순위 기준을 편향제거 MAE로 바꾸고, 편향은 옆에 함께 적어 보정계수로
처리할 몫이 얼마인지 보이게 했다. 전 모델 상관이 0.95를 넘으면 "모델 교체보다
보정계수가 답"이라고 알린다.

제주는 상관계수가 나오지 않는다. Windfinder 값이 8시각 내내 0.5로 고정이라
분모가 0이다. 0으로 채우면 "상관 없음"으로 잘못 읽히므로 None으로 두고 경고한다.

이 지표를 넣자 제주 순위가 뒤집혔다. MAE 기준 파고 1위였던 `ecmwf_wam025`가
4위로 내려갔다. 어제 "파고 1위와 파주기 1위가 갈린다"고 본 것도 상당 부분
편향 때문이었다.

### 그런데 — 검증 기준을 의심하게 됐다

"상관계수 0.98이니 경향성은 이미 맞다"고 결론냈는데, **그 결론이 성급했다.**

`marine-data-audit.md`에 이미 적혀 있던 사실이다.

> Windfinder: *Our global wave forecasts are computed with the global wave
> forecast model **WW3** run by the American Weather Service NOAA.*
> 그리고 **WW3 = NOAA GFS-Wave = Open-Meteo의 `ncep_gfswave025` / `ncep_gfswave016`**

즉 우리 값과 기준값이 **같은 원본 모델에서 나온다.** 독립된 두 소스가 일치한
것이 아니라 같은 답안지를 양쪽에서 본 것에 가깝다. 0.98은 검증이라기보다
동어반복에 가깝다.

### 그러면 진짜 기준은 뭔가 — 셋 다 막혔다

**1) 기상청 부이 실측** — 2026-08-28에 이미 철회된 계획이다(부이 없는 해변,
±0.5m 정확도, "부이와 맞아도 Windfinder와 다르면 사용자는 우리가 틀렸다고 한다").
제주는 구엄·신창 파고부이가 있어 예외인가 싶어 거리를 재봤다.

| 해변 | 구엄(북서) | 신창(서) |
|---|---|---|
| 사계(남서) | 32.6km | 17.9km |
| 중문(남) | 29.9km | 24.5km |
| 월정(북동) | 38.9km | 62.6km |
| 이호테우(북) | **7.1km** | 31.3km |

거리보다 **방향**이 문제였다. 부이 둘 다 서·북서 해안인데 사계·중문은 남향,
월정·김녕은 북동향이다. 남향 해변이 받는 남쪽 스웰을 섬 반대편 부이는 보지
못한다. Surfline이 LOLA→LOTUS로 수심 기반 굴절 계산을 만든 이유가 이것이다 —
부이 값을 그대로 해변 값으로 쓸 수 없다는 전제 위에 만든 시스템이다.
쓸 만한 건 이호테우(7.1km, 같은 북쪽 해안) 정도다.

**2) 사용자 서핑 기록** — 스팟 자체에서 나온 유일한 독립 데이터라 기대했는데,
**서버에 없다.** `SurfRecordRepository`는 기기 로컬 CoreData만 쓰고 업로드
경로가 없다. Firestore에도 `regions`(예보)뿐이고 기록 컬렉션이 없다.
`deviceId`, `payloadVersion`, `lastModifiedAt`, `isDeleted` 필드가 있는 걸 보면
동기화를 염두에 둔 설계지만 지금 붙은 건 Apple Watch 동기화뿐이다.

**3) 수심 기반 변환** — 원리적으로 맞지만 이 프로젝트 규모 밖이다.

### 배운 점 / 다음 액션

**지표를 쪼개니 결론이 바뀌었다.** 같은 데이터인데 MAE 하나로 볼 때와 편향·모양으로
나눠 볼 때 모델 순위가 달라졌다. "어느 모델이 나은가"를 묻기 전에 "지금 지표가
무엇을 재고 있나"를 물었어야 했다.

**기준값의 출처를 확인하지 않고 신뢰도를 말했다.** 0.98이라는 숫자에 먼저
안심했고, 그 값이 우리와 같은 모델에서 왔다는 건 나중에야 떠올렸다. 그것도
새로 알아낸 게 아니라 우리 문서에 이미 적혀 있던 내용이다. **높은 일치도는
그 자체로 검증이 아니다 — 두 값이 독립인지부터 봐야 한다.**

**막다른 길도 기록해 둔다.** 부이 거리표와 "기록은 로컬에만 있다"는 사실은
결론이 없는 조사지만, 적어두지 않으면 다음에 같은 기대를 품고 같은 길을 간다.

다음 — 방향 결정이 필요하다. 지금은 신뢰할 정답지가 없는 상태다.
- (a) 기록을 서버로 올리는 구조를 만든다. 필드는 이미 준비돼 있다. 스팟에서
  나온 독립 데이터가 생기지만 기능 개발이라 범위가 크다
- (b) 검증을 포기하고 Windfinder 기준 편향 보정만 한다. 사용자 기준에는 맞지만
  물리적 정확도는 담보하지 못한다
- (c) 이호테우 한 곳만 부이로 대조해 Windfinder가 얼마나 어긋나는지 본다.
  작게 시작해 (a)/(b) 판단 재료를 만든다

어느 쪽이든 **하루치 편향으로 상수를 박는 일은 하지 않는다** — 예전에 제거한
`+0.5` 보정의 재발이다.

## 세션 4 — Windfinder를 실제로 뜯어보고, 격자 해상도가 진짜 문제임을 확인

### 무엇을

세션 3의 "Windfinder = WW3라 동어반복"이라는 결론을 실제 숫자로 검증했다.
**절반만 맞았다.** 그리고 그 과정에서 지금 구조의 더 큰 문제를 발견했다 —
해변 32곳이 실제로는 격자 20칸으로 접히고, 그 칸이 해변에서 최대 19km 떨어져 있다.

### Windfinder는 뭘 하고 있나 — 속초는 맞고 제주는 아니다

공식 도움말은 명확했다.

> "Our global wave forecasts are computed with the global wave forecast model
> **WW3 run by the American Weather Service NOAA**."
> 지역 모델(EWAM/DWD)은 지중해·발트해만. 오대호는 NOAA.
> — windfinder.com/help/usage/waves.htm

한국은 지역 모델 없이 전지구 WW3다. 후처리·통계보정 언급은 없다.

그런데 숫자를 맞대보니 지점마다 달랐다.

**속초** — `ncep_gfswave025`와 차이가 −0.04~+0.02다. Windfinder가 0.1m 단위로
반올림해 표시하므로 **사실상 같은 값**이다. 공식 설명대로 WW3 통과다.

**제주** — `ncep_gfswave025`와 −0.10~−0.26, `ncep_gfswave016`은 −0.30까지
벌어진다. 반올림으로 설명되지 않는다. 오히려 `ecmwf_wam025`가 −0.06~+0.06으로
맞는다.

결정적으로 **제주 Windfinder가 8시각 내내 정확히 `0.50`으로 고정**이다.
모델들은 0.26~0.56으로 움직이는데 Windfinder만 상수다. 오전에 확인한 기상청
`WAV`가 `0`/`0.5`로 고정이던 것과 같은 모양이다.

**추정: 하한 클램프.** 값이 클 땐(속초 0.7~1.4m) WW3를 그대로 보여주고,
작을 때만(제주 0.3~0.5m) 0.5로 뭉개는 것으로 보인다. 서핑에 무의미한 낮은
파도를 자르는 표시 규칙일 수 있다.

**좌표 문제는 배제됐다.** 페이지 HTML에 실제 지점 좌표가 박혀 있었다
(`href="/#12/33.5142/126.5297/sp:kr158"`). 우리가 `REFERENCE_SPOTS`에 쓰던
값과 소수점까지 일치한다. 속초도 `sp:kr103`, 38.2500/128.5660으로 동일.
같은 지점을 보면서 제주에서만 어긋나는 것이다.

**세션 3 결론 정정** — "동어반복"은 속초에만 해당한다. 제주는 Windfinder 값이
NOAA와 뚜렷이 다르므로 동어반복이 아니다. 다만 그 값이 클램프된 상수라면
**기준값으로 쓸 수 없다**는 점은 같다. 지금 제주 `ncep_gfswave016` 편향
−0.29도 실재하지 않는 편향일 수 있다.

가르는 방법은 간단하다. **제주 파고가 1m를 넘는 날 다시 재면 된다.**
그때도 상수면 클램프 확정, 변하면서 ECMWF를 따라가면 다른 모델을 쓰는 것이다.

### 32곳을 다 비교할 수 있나 — 실제로는 20곳이다

"해변 목록 전부 대조하자"는 질문에서 출발해 Firestore의
`marine_source.grid_lat/grid_lon`으로 세어봤다.

**해변 32곳 → 실제 격자 칸 20개.**

| 격자 | 같은 값을 받는 해변 |
|---|---|
| 38.000, 128.833 | 죽도·인구·기사문·갯마을·남애3리·물치·강릉 남애 (**7곳**) |
| 37.833, 129.000 | 강릉 금진·경포·사천진·사천 (4곳) |
| 36.167, 129.500 | 포항 월포·신항만·영일대 (3곳) |
| 33.708, 126.792 | 월정·김녕 (2곳) |

앱에서 양양권 7개 해변을 눌러보면 파고·파주기가 전부 같게 나온다는 뜻이다.

더 큰 문제는 **격자까지의 거리**다.

| | 거리 |
|---|---|
| 함덕 | 18.63km |
| 포항 신항만 | 17.74km |
| 월정·김녕 | 약 17km |
| 강릉 금진 | 15.48km |
| (가까운 쪽) 다대포 0.62km · 태안 만리포 1.85km · 사계 2.62km | |

해변 앞바다가 아니라 15~19km 떨어진 지점 값을 보여주고 있다.

### 배운 점 / 다음 액션

**"같은 소스니까 동어반복"은 지점을 나눠 봐야 했다.** 세션 3에서 소스가
같다는 사실만으로 전체를 동어반복이라 단정했는데, 실제 숫자는 속초와 제주가
달랐다. 근거 문서(공식 도움말)와 실측을 함께 봤어야 했다.

**기준값이 상수면 편향 계산이 허수를 만든다.** 제주 −0.29는 모델 오차가
아니라 클램프된 기준값과의 차이일 수 있다. `model_compare.py`가 상관계수는
`None`으로 막아뒀지만 편향은 그대로 계산한다 — 여기에도 경고가 필요하다.

**정밀도를 따지기 전에 해상도를 봐야 한다.** Windfinder와 0.05m 차이를 두고
모델 순위를 다투고 있었는데, 정작 우리가 쓰는 값은 해변에서 최대 19km 떨어진
칸에서 온다. 그 오차가 모델 간 차이보다 클 가능성이 높다. 순서가 뒤바뀌어
있었다.
