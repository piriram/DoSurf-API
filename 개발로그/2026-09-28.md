## 1. 첨두주기 배포 — 왜 미루지 않았나

쟁점은 "지금 배포할까, 10/1 에 모델을 확정한 뒤 할까"였다. **지금으로 정했다.**

**과거를 소급 복원할 수 없기 때문이다** (2026-09-27 실측). Open-Meteo 는 과거
날짜에 `wave_peak_period` 를 정상적으로 돌려주지만 **그날 발표된 예보가 아니라
최신 런의 값**이다. 미루는 만큼 그 기간은 영구 손실이다.

미루는 쪽의 이유("한 모델로 일관되게 쌓인다")는 약했다 — 저장이 `merge=True`
라서 나중에 `config.json` 의 `peak_period_model` 만 바꾸면 되고 기존 문서도
안 깨진다.

추가 비용은 세 번째 호출 하루 약 256콜(해변 32 × 8회)이다. 680 → 936콜/일,
무료 한도 10,000 에 여유가 충분하다.

배포 확인: 리비전 `do-surf-functions-00016-w4m` (2026-09-28 09:24 KST).

## 2. 첨두주기가 평균보다 작아지는 것은 정상이다

죽도 06시에 **첨두 2.8초 · 평균 4.3초 · 스웰 4.3초 · 풍파 1.9초**가 나왔다.
첨두가 평균보다 작으니 처음엔 버그로 봤다.

**리서치 결과 정상이다** (NDBC · CDIP). 첨두주기는 **"지금 이 바다를 지배하는
성분"** 을 가리킨다. 풍파가 세지면 스펙트럼 봉우리가 그쪽으로 옮겨가므로
첨두가 작아진다. 업계에 알려진 동작이고 Tp 가 표준이다.

**그때 스웰 주기를 대신 보여주면 안 된다.** "탈 만한 너울이 있다"고 잘못 말하게
된다. 실제로 그 시각의 바다를 지배한 것은 1.9초 풍파였다.

화면에는 `peak_period_s` 만 쓴다. 평균과 섞으면 같은 파도가 8초였다 10초였다
한다 — 서핑 예보는 **9초·12초**를 wind swell / ground swell 경계로 쓰는데
Open-Meteo 평균주기는 첨두보다 1~2초 짧아 그 경계를 넘나든다.

**버그로 보고 고치려 하지 말 것**을 `AGENTS.md` 에 박아 뒀다.

### 동해 대진 — 절벽인지 좌표 오류인지

해안선까지 1.06km 로 판정 기준상 "애매"(1~3km) 구간이었다. **고도 프로파일이
답했다** — 27m 에서 26→20→17→15→12→8→1m 로 **완만하게 감소한다.** 절벽이면
급락해야 한다. 포항 월포(0.94km 내륙, 24m)와 같은 패턴이었다.

내륙 1km 지점이라 육지가 스웰 창을 좁히고 있었다 — 80°(gangneung 최저) → 140°.

### 강릉 남애 — 중복이 아니라 좌표가 바다였다

남애3리를 고친 뒤 `강릉 남애`(gangneung, 37.9347)와 0.9km 가 되어 중복을
의심했다. **리서치로 구조가 밝혀졌다** — 남애항 기준 **북쪽이 3리, 항구·전망대가
2리, 방파제 남쪽이 1리**다. 세 해변이 실제로 따로 있으므로 별도 등록은 맞다.

문제는 `강릉 남애` 가 **해상 3.3km** 였다는 것이다. 스웰창이 240° → 160° 로
**줄었다** — 바다 한가운데서 재면 사방이 바다라 과대평가됐던 것이다.
"스웰창이 넓다"가 좋은 신호가 아닐 수 있다는 걸 여기서 배웠다.

**남은 미결: 지역 분류.** 남애 1·2·3리는 **전부 양양군 현남면**인데
`강릉 남애` 만 `gangneung` 이다. 앱의 지역 탭 구성이 바뀌는 일이라 제품
결정이 필요해서 좌표만 고쳤다.

### 예측이 틀렸다 — 커버리지는 좋아졌다

**"양양 6/6 격자 일치가 깨질 것"이라고 썼는데 반대였다: 16/29 → 18/29.**

물치가 북쪽으로 가면서 `sokcho` 지점이 덮게 됐고(물치·고성 천진·속초 3곳),
영덕 부흥도 `wolpo` 에 들어왔다. `gisamun` 은 6곳 → 5곳이 됐지만 그 5곳은
여전히 완전 일치다.

**틀린 예측을 백로그에 그대로 남겼다.** 지금 커버리지가 좋아 보이는 게
"좌표가 틀려서 6곳이 한 점에 몰려 있기 때문"일 수 있다는 판단 자체는 맞았고,
실제 위치를 반영한 뒤의 숫자가 진짜 값이다.

## 5. 백로그 1번 설계 폐기 — `snap_distance_km` 는 작동하지 않는다

원래 계획은 "수집 격자까지의 스냅거리가 크면 경고"였다. 운영 Firestore 의
스냅거리를 실제로 재 봤다.

| 해변 | 실제 오차 | 수정 전 스냅거리 |
|---|---|---|
| **물치** | **21.5km** | **6.8km** (정상 범위) |
| 강릉 남애 | 3.3km (해상) | 7.3km |
| 함덕 | **오류 없음** | **18.6km** (32곳 중 최대) |

**틀린 좌표도 해안 근처면 스냅이 짧고, 맞는 좌표도 격자가 멀면 스냅이 길다.**
스냅거리는 좌표 오류와 상관이 약하다.

대신 **오늘 실제로 잡아낸 신호**로 설계를 바꿨다.

| 신호 | 잡은 해변 | 도구에 있었나 |
|---|---|---|
| 고도 15m 초과 | 영덕 부흥 40m · 월포 24m · 천진 23m · 대진 27m | ✅ |
| 바다 방위 0/36 | 영덕 부흥 | ✅ |
| 지역 내 좌표 순서 역전 | 물치 | ❌ |
| 인접 해변과 겹침 | 남애3리 (죽도와 0.58km) | ❌ |
| 해상 좌표 (사방이 바다) | 강릉 남애 | ❌ |

뒤의 셋이 없어서 손으로 잡았다. **회귀 테스트 조건을 넣었다** — 오늘 고친
좌표들의 옛 값을 픽스처로 남겨 전부 다시 잡히는지 확인한다.

**수집 경로에는 넣지 않기로 했다.** 좌표는 자주 안 바뀌고, 고도 API 는 파랑
API 와 별개의 일일 한도가 있어 하루 8회 호출하면 막힌다(오늘 실제로 걸렸다 —
32곳 전체 실행이 2,300좌표다).

## 운영 메모

- **고도 API 한도는 UTC 자정 = 09:00 KST 에 풀린다.** 요청 수가 아니라
  **좌표 수로 센다.** 전체를 반복 실행하지 말고 `--region` 으로 나눌 것
- `shore_normal.py --save` 가 기존 파일과 **병합**하도록 고쳤다. 429 로 한두
  곳이 떨어져도 나머지가 지워지지 않는다
- `locations.json` 은 **문자열 치환으로 고친다.** `json.dumps(indent=2)` 로
  다시 쓰면 파일 전체가 재포맷돼 320줄 diff 가 난다(오늘 한 번 그래서 되돌렸다)
