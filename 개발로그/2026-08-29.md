# 2026-08-29

## 무엇을

Phase 1(해상 데이터 정확도 개선)을 실측으로 검증하고 Cloud Run에 배포했다.
검증 과정에서 기상청 파고를 쓸 수 없다는 사실이 드러나 P0의 근거가 확정됐다.

## 왜

Phase 1 코드는 원격 세션에서 작성됐는데, 그 환경에 `KMA_API_KEY`와 Firebase
자격증명이 없어서 **기상청 경로를 한 번도 실행해 보지 못한 상태**였다.
고쳤다고 적어둔 시간대 버그가 실제로 고쳐졌는지 아무도 확인하지 않았다.

또 하나. iOS는 파고를 기상청 값 우선으로 읽는데 Phase 1이 개선한 건
Open-Meteo 쪽이다. 기상청 WAV가 얼마나 자주 채워지는지에 따라 이번 작업이
사용자에게 도달하는지가 갈리는데, 그 답을 모르는 채로 남아 있었다.

## 어떻게

자격증명을 iCloud 인계 폴더에서 찾아 `private/keys/`에 놓고 인수인계 문서의
확인 1·2번을 돌렸다.

**1. 발표시각** — 18:02 KST에 17:00 발표를 골랐다. 아직 안 올라와서 14:00으로
폴백했고 이건 정상 동작이다. 9시간 밀림은 사라졌다.

**2. WAV 채움 비율** — 해변 32곳 전부 66/66. 다른 카테고리(TMP/WSD 등)와 같은
비율로 꽉 찬다. "WAV가 거의 없을 것"이라는 가정이 깨졌다.

여기서 예상 밖의 것이 나왔다. Firestore를 열어 같은 시각 두 값을 대조했더니
기상청 파고가 지역을 막론하고 전부 `0.5`였다. 파싱 버그를 의심하고 API 원본
응답의 `fcstValue`를 직접 찍었더니 원본이 그렇게 왔다 — 지역별로 `0` 또는 `0.5`,
6개 예보 시각 내내 고정. 5km 육상 격자라 해양 파랑모델이 아닌 것으로 보인다.
같은 시각 Open-Meteo는 0.88~1.40으로 지역·시각에 따라 움직인다.

3번(수집 1회 실행)은 건너뛰었다. `run_collection()`이 7일 지난 문서를 삭제하는데,
그건 비용 때문에 의도적으로 넣은 동작이고 스케줄러가 3시간마다 같은 경로를
돌고 있어서 굳이 지금 수동으로 확인할 이유가 없었다.

배포는 `gcloud run deploy`. 이 맥에 gcloud가 없어서 먼저 설치했다.
리비전 `do-surf-functions-00015-szd`, 트래픽 100%, `/health` 정상.

## 배운 점 / 다음 액션

**"확인해 봐야 안다"를 문서에 분기로 적어두면 나중에 그대로 실행된다.**
인수인계 문서가 "WAV가 많으면 A, 적으면 B"로 갈래를 미리 적어둔 덕에,
자격증명이 생긴 시점에 판단 없이 바로 실행하고 결론만 채워 넣으면 됐다.

**의심스러우면 가공 단계가 아니라 원본을 본다.** 모든 지역이 같은 값이면
보통 파싱을 의심하게 되는데, 원본 응답을 한 번 찍는 것만으로 소스의 한계임이
바로 갈렸다. 여기서 파싱 코드를 뒤졌으면 시간을 버렸을 것이다.
